# Архитектура и ограничения

## Логическая схема

```text
HOME-PC
  └── SSH → HA200 (локальная сеть)
         ├── Home Assistant / «Терминал 202» (ingress + ttyd)
         └── SSH over Tailscale → HA202
                                    ├── HAOS / Home Assistant Core
                                    ├── Tailscale add-on (host network, tailscale0, table 52)
                                    ├── Advanced SSH add-on (farhome)
                                    └── csq-socks (Docker bridge)
                                         ├── container network namespace
                                         ├── /dev/net/tun
                                         └── SOCKS5 на 127.0.0.1:1089 *в контейнере*
```

**Важно:** адрес `127.0.0.1:1089` внутри `csq-socks` не означает, что SOCKS-сервис доступен на `127.0.0.1:1089` HAOS. При Docker bridge эти loopback-сети независимы. Команда `csq-socks tun` внутри контейнера также не подключает к туннелю остальные процессы HAOS.

## Наблюдения

- HA202: Linux kernel `6.12.51-haos`, Tailscale `tailscale0` с MTU `1280` в зафиксированном тесте.
- Docker `csq-socks:local`: network=`bridge`; `CapAdd=[CAP_NET_ADMIN, CAP_SYS_ADMIN]`, device=`/dev/net/tun`.
- В контейнере обнаружены `ip`, `python3`, `curl`; штатных `iptables`, `nft`, `socat`, `tun2socks`, `sing-box` при проверке не обнаружено.
- Host route `default` через LAN; Tailscale policy `fwmark` и отдельная таблица `52`. Не трогать их при опытной маршрутизации.
- Для тестового сценария зарезервированы `ip rule pref 10000` и `ip route table 12022`. Это **экспериментальные идентификаторы, не утверждённый production-дизайн**.
- Важное различие путей HAOS: `/share` внутри SSH-дополнения — это не `/share` файловой системы хоста. Для временного контейнера нужная директория наблюдалась под `/mnt/data/supervisor/share/ha202-diag`. Проверять путь на конкретной системе перед любыми действиями.

## Требования к безопасной реализации

1. Не изменять основной `default route` и таблицу Tailscale `52` без подтверждённого аварийного восстановления.
2. Явно сохранять доступ к домашней сети и роутеру, KeenDNS и серверу HA200; не отправлять VPN underlay через тот же обход.
3. Изолировать тестовые правила по `fwmark`/источнику/назначению; **не** начинать с безусловного `from all lookup`.
4. Проверить DNS-поведение, IPv6 и возвратный трафик, чтобы не получить утечки или асимметрию.
5. Watchdog обязан исполняться независимо от SSH-сессии, переживать потерю управляющего соединения и иметь проверенную автономную ветку rollback.
6. Для штатного восстановления нужен отдельный механизм HAOS/Supervisor, а не только процесс контейнера, зависящий от изменённой сети.
7. Маршрутизация и перезапуск сетевых служб **не проводились**; проект остановлен на стадии аудита и экспериментального сторожа.

## Границы публикации

Не размещать реальные: IP Tailscale, MAC, KeenDNS-домен, SSH `authorized_keys`, приватные ключи, пароли, cookie, токены, параметры внешнего обходного сервиса и исходные сетевые отчёты без редактирования.
