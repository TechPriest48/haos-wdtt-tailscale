# HAOS .200 ↔ .202: whitelist routing / bypass — рабочий журнал

**Состояние на 2026-11-07: НЕ ЗАВЕРШЕНО.** Это сохранение результатов работы, а не готовая инструкция по включению full-tunnel.

> Этот раздел ведётся отдельно от основного проекта `wdtt_tailscale`. Публичная версия намеренно **не содержит реальных IP-адресов, SSH-ключей, логинов, доменов KeenDNS и параметров обходного сервера**.

## Цель

Настроить на втором сервере Home Assistant OS (**HA202**) маршрутизацию интернет-трафика через `csq-socks` с политикой белых списков/исключений. Сначала исключить из обхода **весь Tailscale**, локальную LAN, административный SSH, а также доступ через роутер/KeenDNS. Включать Tailscale-приложения в обход только отдельным последующим этапом, не меняя прямой транспорт Tailscale.

Первый HAOS (**HA200**) используется как основная точка управления. Создано отдельное боковое ingress-дополнение **«Терминал 202»**, подключающееся по SSH к HA202 через Tailscale.

## Что реально проверено

- Привязка отдельной боковой панели `Терминал 202` на HA200: работает, веб-сокет `ttyd` устанавливается.
- Ключевая SSH-аутентификация HA200 → HA202: работала; диагностическая команда возвращала `farhome` и маршрут `tailscale0`.
- HA202: Home Assistant Core **2026.7.3**, HAOS **16.3** (на момент диагностики).
- `csq-socks:local` / контейнер `csq-socks`: запущен в Docker `bridge`; отдельный network namespace, SOCKS5 доступен **внутри самого контейнера**.
- `csq-socks` имеет `CAP_NET_ADMIN`, `CAP_SYS_ADMIN`, устройство `/dev/net/tun`; контейнер не привилегированный.
- Прокси выдавал отличный от прямого внешний IP; HTTP и HTTPS через SOCKS5 работали, три последовательных теста HTTPS дали HTTP 200 (~0,8–0,9 с).
- Основной маршрут HA202 был через локальный шлюз, Tailscale обслуживался собственной policy table **52**.
- Временный read-only контейнер с `--network host` видел реальные таблицы HAOS.
- Прототип сценария `routing-safety.sh` был сохранён на HA202; `sh -n` прошёл, режим `status` работал.
- Попытка тестирования 25-секундного watchdog была начата; **факт выполнения ветки rollback достоверно не подтверждён**.

## Последняя нерешённая проблема — приоритет №1

После запуска тестового watchdog подключение HA200 → HA202 через Tailscale перестало отвечать (тайм-ауты SSH/HTTP). Прямая попытка доступа с HOME-PC также не дала HTTP-ответа от HA202. Причина **НЕ УСТАНОВЛЕНА**; причинная связь с watchdog **не доказана и не исключена**.

**Не включать обход и не изменять маршруты, пока KeenDNS/локальный доступ не восстановлен и не исследована причина потери связи.** Не считать проверку watchdog успешной. Не перезагружать HA202 вслепую.

## Файлы, ранее созданные на серверах

- HA200: `/addons/terminal202/` — исходники работающего ingress-терминала.
- HA202: `/config/ha202-diag/diagnose.sh`, `LAST_REPORT.txt`, `PROXY_TEST.txt`, `BASELINE_BEFORE_ROUTING.txt` — локальные диагностики.
- HA202: `/share/ha202-diag/routing-safety.sh` — **непроверенный экспериментальный прототип** для будущего rollback. Не запускать как production-механизм.

Содержимое локальных логов не загружено: там могут находиться внутренние адреса и другие конфигурационные сведения.

## Порядок продолжения

1. Проверить HA202 через **KeenDNS** / другой независимый путь (доступ к роутеру и физический LAN).
2. Сверить `ip rule`, `ip route`, `ip route show table 52`, `ip route show table 12022`, состояние `tailscale0`, состояние SSH-дополнения и Home Assistant.
3. Проверить `/share/ha202-diag/DEADLINE` и `LAST_ROLLBACK_TIME`, журналы тестового контейнера. Не путать результаты команд на HA200 и HA202.
4. Проанализировать безопасность rollback: **сначала независимый механизм восстановления**, затем изолированный тест на обратимой нерабочей таблице.
5. Разработать реальный способ шлюзования трафика: SOCKS5 внутри Docker bridge **не является** маршрутом для всего HAOS. Нужен отдельный tun2socks/TUN-шлюз либо другой документированно совместимый механизм.
6. Зафиксировать исключения (LAN, Tailscale underlay и tailnet, management, KeenDNS/роутер, DNS). Проверять не только Tailscale host-route, но и базовые UDP/DERP-соединения.
7. Тестировать на ограниченном процессе/назначении; только затем расширять правила. Сохранить рабочие ключи SSH и запасной доступ.
